## 1. P0 — `disk stop` 一定失败：**dirty epoch 是一条两端都空着的管道**

### 1.1 现象

```text
execute_operation failed: code=22022 step=service_core.checkpoint_epoch
  detail=The final checkpoint state is invalid
```

文档里把它记成"stop 的 checkpoint 完成判定"。**实际范围比这大**：它是一条
本该贯穿 worker → service 的事实，两端都没有产生者。

### 1.2 三处证据（都不是推测）

**① worker 侧的 "cut" 不是 epoch，是 backing generation。**

`src/host/m5_worker_runtime.cpp:519`

```cpp
candidate.cut_dirty_epoch = impl.runtime->maintenance_stats().generation;
```

而 `DiskMaintenanceStats`（`src/run/disk_runtime.h:86-90`）是
`{dirty_bytes, journal_bytes, generation}` —— `generation` 是 **backing generation**，
与"脏了多少"没有关系。

**② service 侧的 "live" 是写死的 0。**

`src/management/service_worker_control.cpp`，`publish_checkpoint_epoch` 的末尾：

```cpp
return publish(CheckpointEpochObservation{correlation, 0});
```

**③ worker 状态里的 `dirty_epoch` 从来没有被赋值。**

全仓只有三处写 `dirty_epoch` 字段：协议读（`m5_worker_protocol.cpp:312`）、
协议写（`:614`）、和上面那个 generation。
**没有任何一处给它赋真实值** ⇒ `WorkerRuntimeStatus.dirty_epoch` 恒为 0
⇒ `current_dirty_epoch()` 恒返回 0
⇒ `service_core.cpp:3867` 那条"live 比 durable 大就标 dirty"永远不成立。

### 1.3 于是 `clean` 这个判据的含义变成了

`src/management/service_core.cpp:5750`

```cpp
const auto clean = observation.live_dirty_epoch == evidence.correlation.cut_dirty_epoch;
//                = 0 == backing_generation
```

- **create 的第一处 checkpoint 能过**：此时 bundle 还站在 generation 0 ⇒ `0 == 0` ⇒ clean。
- **stop 一定不过**：只要提交过一次，generation ≥ 1 ⇒ `0 != 1` ⇒ dirty ⇒
  `CompletionOutcome::succeeded_dirty` ⇒ `state_machine.cpp:740` 的 `stop` 分支不接受它
  ⇒ `invalid_completion` ⇒ 22022。

**所以这不是"stop 的判定写错了"，而是"stop 恰好第一个把这条空管道用在了会失败的地方"。**
`dbb25a3` 放宽"有序性"之所以看起来有效，是因为 create 的 cut 是 0；它没有、也不可能修好 stop。

### 1.4 影响

- `disk stop` 100% 失败（只要盘上写过东西），T1-05 无法收尾；
- 在它之上的 T1-09（断电恢复）、G3 全部无法验收；
- durable profile 里的 `current_dirty_epoch`、`StopDurableState.dirty_epoch_before`
  现在记的都是 0 或 generation，**恢复路径据此做的任何判断都没有意义**。

### 1.5 修法（五步，顺序不能换）

1. **先修单位**（§2.4），否则 `dirty_bytes` 本身不可信。
2. **把"脏不脏"的判据换成块级 dirty**：worker 侧已有
   `impl.runtime->maintenance_stats().dirty_bytes`。给 `CheckpointEpochObservation`
   增加 `post_commit_dirty_bytes`，由 `publish_checkpoint_epoch` **去问 worker**
   （它已经持有 session），而不是传 0。
3. **`clean = post_commit_dirty_bytes == 0`**，不再比较任何 epoch。
   这正好落在设计的不变量上："是否 dirty 以 worker 报告的 M3 块级 dirty 为准，
   答不出来即 unclean"。
4. **`normal_stop` 不要在 checkpoint 这一步 `complete_command`**：只发布
   checkpoint 已确认的 durable 状态（`phase=stable`、`disposition=committed`、
   `confirmed_generation`、`current_dirty_epoch`），让 remove 系列继续，
   由 `finalize_operation`（`service_core.cpp:6795`）用 stop 的真实 outcome 收尾。
5. **`stop` 表里显式接受 `succeeded_dirty`**（落 `persistence=dirty`）。
   一个"stop 时最后一次 checkpoint 之后又落了写"是合法结局，不是非法状态。

**`cut_dirty_epoch` 要么改成真实计数，要么从 correlation 里删掉。**
留着一个名字是 epoch、值是 generation 的字段，下一个读它的人还会再栽一次。

### 1.6 验收

- 开发机：模型测试驱动 stop，cut 非 0（以前这条路径根本无法在开发机执行）。
- 客机：`create → 写 → stop → 重启服务 → start → forget`，**≥ `-Repeat 20`**。
- 负例：worker 答不出 `dirty_bytes` 时 stop 必须 fail-closed，不能当 clean。

## 2. P1 — 结构性缺陷（会继续产出同类 bug）

### 2.1 步骤级与命令级完成语义混用

`complete_command(plan, outcome)` 的语义是**整条命令的终态**，但 `service_core.cpp`
里有 **14 处**调用，其中大多数发生在计划**中途**。每个中途调用点都必须挑一个
"表里恰好接受"的 outcome —— 于是语义被表决定，而不是被事实决定。

已知被这一形状咬过的：`terminate_process` 少要权限、拆卸挂在 `drive_letter_assigned_`、
reclaim 动词缺 `started_` 前置、dispatch 落 default（§2.2），现在轮到 stop。

**修法**：拆成两个函数 ——
`apply_step(plan, step, StepOutcome) -> ProfileState`（步级，不产生终态）与
`complete_command`（只允许在终点调用）。再加一张
`10 命令 × 10 outcome` 的合法/非法表测试（今天只有 6 处引用 `complete_command`）。

### 2.2 `default: return unrealized` 会吞掉新动作

`src/management/service_worker_control.cpp:1150`。新增 `ActionKind` 若忘了加 case，
运行期变成"没有 worker 做过这件事"，且所有不覆盖它的测试照样全绿。
`part 16` 的注释自己写过这个教训，但代码仍然留着 default。

**修法**：删掉 `default:`。仓库已开 `/W4 /WX`，漏一个分支就是编译错误。
成本一条语句，收益是"以后不可能再静默"。

### 2.3 profile 的内存策略：配置面有，执行面没有

| 层 | 状态 |
|---|---|
| CLI | `--memory-mode`、`--memory-hard-limit`（`cli_parser.cpp:291-310`） |
| profile | `memory_mode/hard/soft/low_watermark` 编解码、校验、持久化齐全 |
| **执行** | **不存在** |

证据链：

- `DiskRuntimeOptions`（`disk_runtime.h:118-123`）**没有内存字段**；
- worker 构造 `ProductionRuntimeAdapter::Config` 时把 `ram_limit_bytes` 写死 **0**
  （`m5_worker_runtime.cpp:312`）；
- `store_options_for(0)` 直接返回 `production_store_options()`
  ⇒ 硬上限 **1 GiB**、软上限 512 MiB（`m3_provider.cpp`）。

**后果**：用户设 8 GiB 得到 1 GiB；设 256 MiB 也得到 1 GiB。**开关是假的，而且不报错。**
这是项目自己列为"最容易断"的那类跨层事实（volume identity / bundle evidence / image uuid
之后的第四次）。

**修法**：`DiskRuntimeOptions` 增加 `memory_hard_limit_bytes`（+ mode），worker 从 profile
传下去，`store_options_for` 用它；加单测断言"store 的 hard_limit == profile 的值"。
**"0"必须显式定义为"未配置"并在 `disk show` 里显示为默认值**，不能静默。

### 2.4 `dirty_bytes` 单位错 **32 倍**

`src/run/runtime_adapter.cpp:576`

```cpp
constexpr std::uint64_t kBlockBytes = 2ULL * 1024ULL * 1024ULL;   // 2 MiB
return {(stats.resident_dirty_blocks + stats.zero_dirty_blocks) * kBlockBytes, ...};
```

而块大小是 **64 KiB**（`src/storage/block_constants.h:7`）。

**后果**：`run_loop.cpp:43` 拿它跟 `--checkpoint-dirty-mb` 比 ⇒ 脏阈值提前 **32 倍**触发
（设 64 MiB，实际 2 MiB 就提交）；T1-07 要暴露的 `resident_bytes` 也会直接错。

**修法**：改用 `storage::kBlockSizeBytes`；加单测（N 个脏块 → 恰好 N×64 KiB）。
顺带一提：`maintenance_stats()` 的另外两处消费（worker status 的 `dirty` 布尔、
`cut_dirty_epoch`）因为只取值非零/取错字段，所以这个 bug 一直没暴露。

### 2.5 `service_core.cpp` 7.9k 行，且开发机零覆盖

`src/management` 共 21k 行，它一个文件占 7.9k，承载全部命令执行。
开发机上对它的直接测试是 **0**：`m5.service_orchestration` 测的是纯函数，
`m5.service_host` 测的是端点；执行循环只有客机端到端。

**结果**：每个缺陷都要 5–30 分钟的客机往返才能发现——这也解释了为什么
270 个提交里 146 个是文档（大量"记录这次又发现了什么"）。

**修法**：不要求一次性拆完。随 §2.1 的重构，把 create / checkpoint / stop 三条的
**决策**抽成纯函数，**执行**留在原处。目标是让"stop 在 cut≠0 时应该成功"这类断言
能在开发机 50 ms 内跑完。

## 3. P2 — 验证与工程

### 3.1 没有 CI，本地/客机边界只写在散文里

154 个 ctest **没有任何 label**；哪些能在开发机跑只写在 `AGENTS.md` 里。
一次误选就会留下孤儿 worker，把开发机存储栈拖到要重启（他们自己的记录）。

**修法**：`set_tests_properties(... LABELS "local")`，`ctest -L local` 作为提交门，
CI 只跑 local；VM 用例单独一个手动任务。**这一步的收益是之后每一步都变快。**

### 3.2 测试并行不安全（已复现）

```
-j 4: unit.m5.worker_private_pipe  ***Failed (server.ok() @ tests/unit/m5_worker_private_pipe_tests.cpp:179)
       unit.m5.service_worker_session  Passed 40.03 sec   ← 单独跑 0.02 s
单独跑: 通过
```

两者都用 `private_pipe_name(profile_id(), 7)`，而 profile id 是写死的
`11111111-2222-3333-4444-555555555555`。

**修法**：管道名加进程/测试唯一后缀（pid + 原子计数），或给这两条加 `RUN_SERIAL`。
**在 3.1 之前必须先修这个**，否则 CI 一上 `-j` 就是红的，还是假红。

### 3.3 干净会话里构建入口不成立

两条都是实测：

```powershell
cmake --build out/build/msvc --config Release
# → LINK : fatal error LNK1181: 无法打开输入文件"bcrypt.lib"（看起来像缺 SDK）
```

1. 必须先 dot-source `tools/Enter-MsvcEnvironment.ps1`（否则没有 LIB/INCLUDE）；
2. 而该脚本**会被 ExecutionPolicy 拒绝**（"未对文件进行数字签名"），
   必须再 `Set-ExecutionPolicy -Scope Process Bypass`。

**修法**：一个 `tools/build.ps1` 把三件事做掉（进程级 policy + devshell + cmake），
文档只写这一条。现在的手册要求执行者记得三件事，忘一件就得到一个像"缺 SDK"的报错。

### 3.4 T1-06 是下一个关键路径项，正例为零

`reconcile_checkpoint` 在测试里只有 **5 处**引用；设计 §14.3 有七条用例。
而它是 G3（断电恢复）的判定核心，也是 P0 修完之后紧接着要做的增量。

**修法**：照 `m3_checkpoint_crash_model_tests.cpp` 的做法，先写七条模型用例再改实现。

## 7. 这些问题分布在哪些层

"前五层没问题"是一个需要折价的结论：它们各自**在自己原来的入口上**通过了验收，
但这次找到的问题里至少两条不在 M5。

| 问题 | 落在哪层 | 为什么之前的验收没抓到 |
|---|---|---|
| dirty epoch 空管道（§1） | **M5**（service ↔ worker 接缝） | 两端各自都"能编译、能跑通 create" |
| `complete_command` 中途调用（§2.1） | M5 | 只有跨步骤的用例才能暴露 |
| `default: return unrealized`（§2.2） | M5 | 加新动作时没有测试 |
| 内存策略不生效（§2.3） | **M5 ↔ M4 接缝** | M4 从 CLI 拿 2 GiB 默认值；worker 传 0，走的是另一条路 |
| `dirty_bytes` 错 32 倍（§2.4） | **M4**（`run/runtime_adapter.cpp`） | 所有测试都喂 fake stats，**没有一条断言过这个实现算出来的值** |
| 构建入口（§3.3） | 全仓 | 之前每个会话都手工 `Enter-MsvcEnvironment`，没人从冷会话试过 |
| 并行测试不隔离（§3.2） | M5 测试 | 一直串行跑 |
| `auto_start` 只存不用（§4.1） | M5（T1-09 未做） | 本来就没实现 |

**M5 之所以看起来"全是它的问题"，是因为它是唯一一层不新增算法、只新增接缝的层**：
服务↔worker、worker↔引擎、命令↔计划、配置↔执行。接缝没法用"这一层自己的单测"证明，
只能靠跨层断言——而那正是目前最薄的地方（`service_core` 7.9k 行、开发机零覆盖）。

**前五层的证据强度也不一样**：

| 层 | 证据 | 强度 |
|---|---|---|
| M0 / M1 | 开发机 + 客机间接覆盖 | 中 |
| M2 | 动态块存储验收（468 行）+ 20/20 稳定性 | 强 |
| M3 | 冻结证据、崩溃矩阵、Formal soak（1826 行验收） | 强 |
| M4 | **5 个 VM 场景**（VM-1…VM-5）+ 465/465 目标构建；报告自己写明"qualification 包没有完整保留" | **中**——是观察报告，不是完整套件 |

所以更准确的说法是：**没有新证据表明 M0–M3 有问题；M4 的证据是窄的；所有新问题都落在
M4 尾部与 M5 的接缝上。**

**要真正回答"前五层有没有问题"，唯一诚实的办法是 T1-09**：用 M5 的入口（服务 + 开机自动恢复）
重跑一遍 M3/M4 的承诺（断电后恢复到最后完整 generation）。在那之前，
"前五层没问题"应当读作"没有新证据表明有问题"，而不是"已经证明没问题"。
