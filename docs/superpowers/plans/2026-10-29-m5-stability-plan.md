# M5 对外稳定版待做清单

**日期**：2026-10-29
**定位**：从“单盘试点可用”到“可以对外承诺稳定”的发布门禁清单。不是功能愿望清单：
P0/P1 是门禁，P2 是后续版本。

## 0. “对外稳定”的判定

满足下面全部条件，才可以对外说“稳定”：

1. 陌生用户在**受支持平台**上，按文档完成安装；驱动缺失时有明确提示，不是启动失败。
2. **单盘**数据在正常停止、硬断电、worker 崩溃、service 崩溃、bundle 损坏、磁盘满、
   权限错误下，行为可预测：已提交数据不丢；未提交数据最多丢一个 checkpoint 间隔或
   64 MiB（两者取先）；不挂死、不残留设备/worker。
3. 第二块盘被**明确拒绝**，而不是“看起来能建、拆卸时留下残留”。
4. `--accept-volatile-data-loss` 的语义在 service 和 worker 两侧一致；脏盘卸载/强制停止可预期。
5. 发布有**可重复证据**：一条命令跑完全量套件；manifest 冻结；干净 VM 上的安装/卸载/升级读数。
6. 已知限制写在文档里（单盘、卷标、簇大小、导出仅停机、驱动前置），不靠用户猜。
7. 升级、覆盖安装、回滚、脏盘卸载至少各有一条客机读数。
8. 安全边界经过对抗性审计：pipe ACL、路径/重解析点、服务与 worker 权限、job object、
   二进制/配置 ACL。

**当前不满足**：第 2、3、5、7、8 条；第 6 条部分满足（usage §6 已写单盘/release-memory）。
G1/G2/G3 与 T4-04 已通过，全量回归 158/160（两个 `vswhere` 环境失败）。

## 1. P0：不关闭不得对外

### STAB-01 单盘硬保护

**现状**：M5 是单盘产品，但用户可以创建第二块盘；同时挂两块时，第二块的拆卸不会真正
移除设备（`no volume carries the recorded identity`、`forget device_absent=0`）。
**为什么是 P0**：这比“不支持多盘”更危险——它看起来支持，实际会留下残留设备。
**要做**：
- `disk create` / `disk start` 在已有 running 盘时返回稳定错误码，文案明确“单盘产品”；
- 或在 service 的 admission 层拒绝第二个 lifecycle reservation，并写日志；
- e2e 断言：第二块盘被拒绝，第一块盘的 generation/挂载/worker 全部不变。
**验收**：客机 `cli_e2e` 新增一段：建第一块 → 建第二块得到明确失败 → 第一块仍可 checkpoint/stop；
`device_absent=1` 对第一块成立，第二块没有留下设备。

### STAB-02 内存耗尽行为

**现状**：只做了“内存压力 → best-effort checkpoint”（T1-08）；没有“RAM 真的不够”的读数。
动态内存盘最怕这个。
**要做**：
- 定义并实现耗尽策略：写入返回明确错误（不挂死）、已提交数据不受影响、checkpoint 仍可完成；
- 若产品选择“超卖到失败”，把失败码和恢复步骤写进文档；
- 客机实验：把 RAM 压到接近 virtual size，记录写入失败、`disk show`、checkpoint、重启恢复。
**验收**：客机读数：耗尽时写失败可预期、无 worker/设备残留、重启后最后提交 generation 完整；
文档写明“最多丢多少、失败长什么样”。

### STAB-03 M5 层故障矩阵

**现状**：P4/P5 提交边界只在 M3 故障注入层覆盖；bundle 损坏、bundle 磁盘满、权限拒绝、
worker 被杀、service 被杀、连续重启，没有 M5 产品级读数。
**要做**（每条都要有客机读数）：
1. 硬断电定点打在 checkpoint 的 P4/P5 之间（可重复的注入点，不是随机时刻）；
2. bundle 文件损坏/截断 → 明确 `needs-attention`，不重新格式化、不猜；
3. bundle 所在卷满 → create/checkpoint 明确失败，已提交代仍可恢复；
4. ProgramData 权限被改坏 → 启动明确报错，不静默降级；
5. worker 在 checkpoint 中途被杀 → service 不挂死，operation 终态，重启可恢复；
6. service 在 operation 中途被杀 → 重启后 reconcile 到确定状态；
7. 连续 3 次断电重启 → 每次都能回到最后提交代，无累积残留。
**验收**：每条一个 e2e 或脚本 + 客机读数；失败路径的 error code 进入错误目录（STAB-11）。

### STAB-04 CI 一键全量

**现状**：全量 160 一个请求会卡在 agent 请求队列重放；`powerloss_prepare` 的 results.json
偶发写成 357 个空格；`structural` 依赖 `vswhere`，缺失时 FAIL 而不是 SKIP；只能人工按组跑。
**为什么是 P0**：没有可重复的一键证据，就不能承诺“这个版本没坏”。
**要做**：
- harness 每次启动前清空/隔离请求队列，或按 request id 只处理本次请求；
- results.json 原子写（临时文件 + rename），写坏时明确失败；
- 测试分组由 harness 内部完成（unit / model / integration / powerloss），对外仍是一条命令；
- `vswhere` 缺失 → SKIP 并写明原因，不计 FAIL；
- 全量跑完输出机器可读的 `results.json` + 人读摘要。
**验收**：干净客机一条命令跑完 160，结果稳定；连续两次结果一致；两个 `vswhere` 用例是 SKIP；
`powerloss` 三段自动串起来；总时长有记录。

### STAB-05 支持平台与驱动前置

**现状**：只在 Windows 11 x64 一个 VM 上验收；安装器只检查 `phdskmnt`、不安装；
没有支持矩阵和驱动版本要求。
**要做**：
- 明确支持矩阵：Windows 11 版本（至少 22H2/23H2）、Windows 10 22H2 是否支持、Server 是否支持；
- 驱动版本下限检查；缺失/过旧时给出可操作的提示和文档链接；
- 至少在两档 Windows 上跑 install + cli_e2e 冒烟；
- 记录已知不兼容的驱动/AV/EDR 组合（至少做一次 Defender 开启的冒烟）。
**验收**：矩阵每一格有“通过/不支持/未测”的明确标记；驱动缺失的失败信息可操作。

### STAB-06 升级 / 覆盖安装 / 回滚 / 脏盘卸载

**现状**：install/uninstall、`-PurgeData`、脏盘卸载有读数；覆盖安装、旧版本数据迁移、
回滚没有。
**要做**：
- 覆盖安装：同一版本重装、旧版本 → 新版本，profile/bundle 不被破坏；
- 数据格式版本检查：不兼容时拒绝启动并说明，不静默迁移；
- 回滚：新版本失败后装回旧版本，数据仍可读（或明确“不可回滚”并文档化）；
- 脏盘卸载：`-AcceptVolatileDataLoss` 与拒绝路径各一条读数。
**验收**：干净 VM 上 install → create/write/checkpoint → 覆盖安装 → start/verify → 卸载，
数据与 generation 一致；回滚路径有明确结论。

### STAB-07 安全边界对抗性审计

**现状**：public pipe 有 owner/admin 授权；没有对抗性审计。
**要做**（按威胁列，不按代码列）：
- pipe 冒充/重放：非授权用户能否发命令、能否拿到别人的 operation；
- 路径：bundle 路径中的 `..`、符号链接/ junction、重解析点，能否让服务写错位置；
- 服务/worker 权限：worker 是否以过高权限运行、job object 能否被逃逸；
- 二进制/配置 ACL：非管理员能否替换 service/worker/配置；
- 日志/诊断是否泄露路径或令牌。
**验收**：每条威胁有“已阻断/接受风险”的结论；阻断项有测试或代码证据；接受风险写进文档。

### STAB-08 发布工程与版本

**现状**：manifest 冻结与 validator 已有；版本号、changelog、签名、校验和、可重复构建
没有形成发布流程。
**要做**：
- 语义化版本 + `--version`（CLI/GUI/service 一致）+ changelog；
- 安装包/二进制签名确认（至少 Authenticode；没有证书就明确“未签名”并承担 SmartScreen 后果）；
- SHA-256 校验和随发布附上；manifest 与发布物一一对应；
- 发布说明模板：支持平台、驱动要求、已知限制、数据丢失上限、回滚方式。
**验收**：一次完整发布演练：构建 → 冻结 → 签名/校验和 → 干净 VM 安装 → 冒烟 → 卸载；
所有产物可追溯到同一个 commit。

## 2. P1：GA 前必须关闭

### STAB-09 非提权 GUI 只读 e2e

**现状**：`gui_view_model` 有 `needs_elevation` 提示，`m5.gui` 模型用例覆盖；没有非提权 e2e。
**要做**：非提权启动 GUI → 能 list/show → 修改操作被拒并显示明确提示 → 不崩溃。
**验收**：客机一条非提权 e2e 读数；截图或日志证明提示出现。

### STAB-10 性能基线

**现状**：没有吞吐/延迟/内存开销基线；checkpoint 停顿没有上限承诺。
**要做**：1 GiB 盘的 create/start/checkpoint/stop 延迟；顺序/随机写吞吐；checkpoint 期间
I/O 停顿；每盘内存开销；worker 启动时间。给出“典型值 + 最坏值”。
**验收**：一台受支持 VM 上的可重复基线；文档写“不承诺 SLA，但给出实测范围”，或明确 SLA。

### STAB-11 长时 soak 与资源泄漏

**现状**：T1-07 做过 20 次重复；没有 24–72 小时连续 create/write/checkpoint/stop/断电。
**要做**：至少 24 小时循环 + 每 N 轮一次硬断电；监控 handle/worker/内存/代增长。
**验收**：无 handle/worker 泄漏；内存回到基线附近；每轮恢复正确；日志无未解释错误。

### STAB-12 卷标决策

**现状**：整条链已建，但 AIM 卷上 `SetVolumeLabelW` 永不返回；用户入口已撤回。
**要做**：二选一——(a) 换路实现（短命进程 / `FSCTL_SET_VOLUME_LABEL` / 驱动确认）；
(b) 正式标记“不支持”，删除或隔离死代码，文档写明。
**验收**：有明确的“支持/不支持”结论；不支持时 `--volume-label` 的帮助与错误信息一致。

### STAB-13 诊断与支持包

**现状**：service.log、`disk show`、operation record 有；没有一键支持包/环境信息。
**要做**：`myrd-cli support-bundle`（或脚本）：版本、OS/驱动版本、服务状态、profile 列表、
最近日志、operation 历史、manifest；自动脱敏路径/令牌。
**验收**：陌生用户能生成一个包；包能解释一次失败，不需要远程登录。

### STAB-14 文档与 UX 收口

**现状**：usage 有“不做的事”；卷标、簇大小、导出仅停机、驱动前置、单盘限制分散。
**要做**：一页“支持范围/已知限制/数据丢失上限/备份与导出/驱动要求/卸载注意”；安装器与
CLI 错误信息指向这一页。
**验收**：文档评审通过；每条已知限制有对应测试或明确“未测”。

### STAB-15 §8 收尾与测试路径

**现状**：master-plan §8 第 0 项（镜像格式化/簇大小）未清；第 3 项（测试烘入源码树绝对路径）
降级为改进项但未修。
**要做**：
- 簇大小/格式化：明确“不做”并写进支持范围，或立项实现；
- 测试路径：改为环境变量/相对路径，使测试可在非镜像布局运行。
**验收**：§8 每项有“关闭/明确不做”的结论；完成口径不再有悬空项。

### STAB-16 兼容性扩展

**现状**：只有 Windows 11 x64 一个 VM；没有 Win10/Server、不同磁盘/文件系统、AV/EDR 组合。
**要做**：至少 Win10 22H2 冒烟；NTFS 压缩/加密目录上的 bundle 路径；Defender 开启冒烟；
非系统盘/不同扇区大小（若支持）。
**验收**：矩阵更新；每个“不支持”有明确错误，不是挂死。

## 3. P2：后续版本，不阻塞对外稳定

- `disk release-memory`（显式释放；自动 UNMAP 已生效）
- 容量在线调整（扩容/缩容）
- 热导出 / 运行中导出
- VHDX 导入（当前只导入 bundle）
- 快照 / 克隆
- 网络共享 / 压缩（产品线外）
- G4 多盘同时运行与延迟隔离
- 簇大小/镜像格式化（若 STAB-15 决定不做，则长期留在“不支持”）

## 4. 发布门禁（全部打勾才可对外）

- [ ] P0 全部关闭，且每条有客机读数
- [ ] P1 全部关闭，或有用户书面接受的例外
- [ ] 一条命令跑完全量套件；连续两次结果一致；环境缺失是 SKIP 不是 FAIL
- [ ] G3 硬断电定点 P4/P5 通过；连续 3 次断电恢复通过
- [ ] 干净 VM 上 install → 使用 → 升级 → 回滚 → 卸载全链路通过
- [ ] manifest 4 binaries + 全部 readings，validator `accepted`
- [ ] 安全审计结论：阻断项已修，接受风险已文档化
- [ ] 支持范围/已知限制/数据丢失上限/驱动要求一页文档发布
- [ ] 版本号、changelog、校验和、签名（或明确未签名）齐备
- [ ] 支持包可生成，且能解释一次真实失败

## 5. 建议顺序（按证据关闭，不按日期关闭）

**阶段 H1（先保命）**：STAB-01、STAB-02、STAB-04。
先让“第二块盘不会留下残留”“内存耗尽不会挂死”“一条命令能证明没坏”成立。

**阶段 H2（再保恢复与交付）**：STAB-03、STAB-05、STAB-06、STAB-07、STAB-08。
把故障矩阵、平台/驱动、升级/回滚、安全、发布工程补齐。

**阶段 H3（GA 前收口）**：STAB-09 ～ STAB-16。
非提权 GUI、性能基线、soak、卷标决策、支持包、文档、§8、兼容性。

**一句话**：H1 结束可以叫“单盘稳定版”；H2 结束可以叫“可对外交付的 RC”；H3 结束才是
“可以承诺稳定的 GA”。
